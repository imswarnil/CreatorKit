## 0. The headline finding — read this before anything else

The brief that framed this work says *"`design.imswarnil.com` — an old design system /
component generator. The generated components section UI is disorganized and has no
proper documentation."*

**That is no longer true of `design.imswarnil.com`.** It was rebuilt. What is actually on
disk is two design systems in one folder:

| | Path | Package name | State |
| --- | --- | --- | --- |
| **New** | `design.imswarnil.com/` (root) | `@imswarnil/swarnil-design` | Rebuilt, 7 layers, **65 documented pages**, live-demo docs generator, git-tracked, clean |
| **Old** | `design.imswarnil.com/old-design/` | `creator-design-system` | The system the brief describes. Sprawling docs, **completely untracked by git** (0 files in the index) |

`old-design/` being untracked matters a lot: it is a local leftover, not part of the
`Swarnil-Design-System` repo history. **Moving it out costs nothing and deletes nothing
from any repo.**

And the two Ghost themes split cleanly along the same line:

- `Imswarnil.com` theme → built on the **old** system (`creator-design-system`).
- `signal` theme → built on the **new** system (`swarnil-design`).

So the split you asked for already exists in the code; it just has not been given
folders yet. The migration is mostly a *move*, not a *rewrite*.

## 5. Where design tokens live

Four places today, in this order of authority:

1. **`old-design/src/1-foundation/`** — `01-color.css`, `02-typography.css`, `03-space.css`,
   `04-elevation.css`, `05-motion.css`, `09-logo`, `11-shape`, `12-frame`, `13-cutout`.
   Raw CSS custom properties on `:root`, oklch colour. This is what the `Imswarnil.com`
   theme actually consumes. **This is the creator kit's real token source.**
2. **`design.imswarnil.com/src/1-foundation/`** — the rebuilt ladder. Also oklch, but a
   different palette naming scheme: `--ink-0…1000` (14 steps), plus accents
   `--signal-*`, `--craft-*`, `--mint-*`, `--azure-*`, `--rose-*` (11 steps each).
   Plus `src/0-config/properties.css` (23 registered `@property` declarations, which the
   old system does not have).
3. **`Imswarnil.com/assets/css/0-foundation/tokens.css`** — a **bridge file, not a source**.
   12 declarations, all of them either `var()` of a system token or a layout constant the
   system can't know: `--nav-h`, `--nav-gap`, `--header-offset`, `--w-article`,
   `--w-listing`, `--w-player`, `--page-top/gap/bottom`, `--gh-content-width`,
   `--gh-wide-width`. Its own header states the rule: *"No new colour values. No new radii.
   No new durations."* **The theme is disciplined. There are no rogue tokens in it.**
4. **`tailwind.config.js`** in the theme — Tailwind is present for *utilities only*
   (`@tailwind base/components/utilities`), explicitly not for defining appearance.

## 8. Recommended package boundaries — and a recommendation you should read before Phase 1

### 8a. The architecture question

The phased brief specifies React + TypeScript strict + CVA + Radix + Storybook + Turborepo.
**None of that exists in this codebase, and two of the three things being migrated cannot
consume it.** Ghost themes are Handlebars rendered server-side by Ghost; they consume CSS
classes. A React component library is unusable by `themes/creatorkit-ghost` and by the
HTML templates and the YouTuber portfolio you asked for.

Building React components would mean authoring every component **twice** — once as CSS for
Ghost and the HTML templates, once as JSX — and keeping them in sync forever. That is the
single most expensive possible shape for this repo, and you asked me not to waste tokens.

**Recommendation: CSS-first kit, framework-agnostic.** Ship `@creatorkit/tokens` and
`@creatorkit/ui` as CSS. Every consumer — Ghost, static HTML templates, the Next.js
project, a future React app — imports the same stylesheet and uses the same class names.
Zero duplication. If React ergonomics are wanted later, add `@creatorkit/react` as a thin
optional package of typed wrappers over the same classes — additive, and only for the
components that genuinely need behaviour (Dialog, Menu, Tabs, Carousel). I would defer
that past v0.1.0.

TypeScript still earns its place — in the tooling (`tools/component-gen`, build scripts)
and in the Next.js app. Not in the component layer.

### 8b. Proposed boundaries

```
creator.imswarnil.com/
├─ packages/
│  ├─ tokens/        @creatorkit/tokens
│  │                 Authored once. Emits CSS custom properties, a Tailwind preset,
│  │                 SCSS vars, and typed JS exports. Depends on nothing.
│  │                 WHY: the theme's own tokens.css already proves this boundary is
│  │                 real — it consumes tokens and adds only layout constants.
│  ├─ core/          @creatorkit/core
│  │                 Reset, base elements, focus ring, layout primitives, cascade
│  │                 layer registration, the small JS helpers (nav.js, highlight.js).
│  │                 WHY: old `1-foundation` minus tokens is exactly this, already.
│  ├─ ui/            @creatorkit/ui
│  │                 Elements + components + patterns + sections. The kit.
│  │                 WHY: it is one CSS bundle in practice; splitting further would
│  │                 create packages nobody imports independently.
│  ├─ collections/   @creatorkit/collections
│  │                 The 24 `.c-*` content types + the 13 per-collection bundles.
│  │                 WHY: this is creator-domain vocabulary (video, course, episode,
```
